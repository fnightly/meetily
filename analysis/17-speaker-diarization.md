# 说话人分离：架构决策与已实现部分

## 一、发现了一个真实的运行时风险（必须先说）

我们已有的 ONNX 用法与 `sherpa-onnx` **会冲突**：

| 组件 | ONNX Runtime 用法 |
|---|---|
| 我们（Parakeet） | `ort 2.0-rc.10` + **`load-dynamic`**，运行时 `ort::init_from("onnxruntime.dll")` |
| `sherpa-onnx` | 自带 `sherpa-onnx-sys`，**链接自己的 ONNX Runtime** |

在 Windows 上把两份 ONNX Runtime 加载进同一进程，是**运行时崩溃的经典来源**。最糟的是它**编译能过**，只在真实录音转写时才炸。

### 但有一条不需要第二个运行时的路

我检查了我们打包的 `onnxruntime.dll`：

```
OrtGetApiBase                               存在 ✅
OrtSessionOptionsAppendExecutionProvider    存在 ✅
```

**它已经导出 ONNX Runtime C API。** 这意味着可以用**我们已有的 `ort`** 直接加载分离模型：

- 分割模型（Pyannote segmentation 的 ONNX 导出）
- 说话人嵌入模型（如 NeMo/CAM++ 的 ONNX 导出）
- 聚类 → **我们自己的代码**

**结论：走 `ort` 直载模型，不引入 `sherpa-onnx`。** 零新依赖、零符号冲突，且复用我们已有的模型下载 / 镜像源 / 磁盘空间预检基础设施。

代价：需要自己处理模型的输入输出张量形状。但分离这一块的**两个算法部分都是我们的**，且已经写完并测过（见下）。

## 二、已实现：分离流程里属于我们的两个算法

模型只输出**嵌入向量**和**分割概率**；"谁是同一个人"和"这句话是谁说的"是本应用的逻辑，也是决定结果读起来对不对的部分。两者都**无依赖、可完整测试**。

### 1. 说话人归属对齐（`audio/speaker_turns.rs`，18 测试）

把分离得到的 `(start, end, speaker)` turns 与转写片段按时间对齐。

**按总重叠时长决定**，而不是"谁先遍历到"——因为一个片段常跨越说话人切换（一个人说完、另一个接上）：

```
片段 [3.0, 7.0]  vs  turn A [0,5] / turn B [5,10]
  A 重叠 2.0s，B 重叠 2.0s → 平局，按较低索引决胜
片段 [4.0, 9.0]  →  A 1.0s，B 4.0s  →  B
```

- **同一说话人的多个 turn 重叠要累加**再比较（一个说话人可能有多个不连续 turn）
- 无重叠时**回退到最近的 turn**：落在两个 turn 之间的片段几乎总是其中一个的延续，不归属会在转写里破洞
- 平局按**较低 speaker 索引**决胜，保证跨运行可复现
- 零长度片段、空 turns、乱序 turns 都有测试

### 2. 嵌入聚类（`audio/speaker_cluster.rs`，17 测试）

**层次聚类 + 平均链接 + 余弦距离阈值**，而不是 k-means——因为**没人知道一场会议会有几个人说话**，k-means 需要预先指定 k。

- 余弦**只看方向不看长度**（否则大声的片段会显得不像同一个人）
- 零向量 / 维度不匹配**返回 0 而不是 NaN**（一个退化的嵌入不能污染整轮聚类）
- 合并顺序**确定性**（等距时选更早的配对）
- 说话人编号**按首次出现**，所以"说话人 0"就是第一个被听到的人，而不是合并顺序的副产物

## 三、被自己的测试抓出的两个 bug

### 1. 说话人预算实际上没有生效

第一版的合并条件结构是错的——一个会突破预算的合并照样执行。测试 `the_speaker_budget_is_respected` 直接抓出来。

### 2. 我搞错了 `max_speakers` 的语义

修完上个 bug 后，另一个测试报 `left: [0,1,2]`、`right: [0,0,0]`：**三个完全相同的向量没有被合并**。

原因：我把"最多 8 个说话人"实现成了"**至少** 8 个"——预算检查无条件触发，把 3 个簇的合并直接拦住。

正确语义是：`max_speakers` **只在初始簇数多于该上限时才约束合并**。否则完全由阈值决定。

修正后：3 个相同向量 → 1 个说话人；8 个正交向量 + 阈值 1.5 + 预算 3 → 至少保留 3 个。

**这是我这轮第二次被自己的测试抓出设计错误**——上一个类似错误是聚类的最小重复单元（见 `analysis/16`）。
